# Development Rules

规则分为强制、推荐和例外。只有代码、测试、已执行决策或多模块稳定实践支持的内容才列为强制。

## 强制规则

### 多 Agent 协作

- 改动文件前先认领任务，并在 `.agent/TASK_BOARD.md` 登记。
- 并行任务使用独立的 Git 分支或 worktree；记录预期文件范围与活动锁。
- 保留无法解释的和未合并的改动；暂停或转移工作前更新 `.agent/TASK_HANDOFF.md`。
- 除非被明确要求，否则不得提交或推送。

### 代码与安全

- 不提交密钥、数据库连接信息、用户标识明细和运行数据。
- 改动保持最小，仅限于已认领范围；不顺带重构无关区域。
- 新依赖必须说明现有方案不能满足的理由，并更新 lockfile。
- 删除旧实现前确认所有消费者、测试和文档已迁移，不保留无调用的双实现备用。

### 测试与验证

- SQL、校验、聚合、存储、任务、API、导入导出和缺陷修复必须有自动化测试（按技术栈）。
- 不得删除或弱化测试以让任务通过；不得静默吞错、伪造数据或把 Mock 当生产结果。
- 失败测试不能通过删除断言或静默降级规避；若失败与本任务无关，记录证据并保持本任务范围。

### 代码-文档同步门禁

- 修改前在计划中逐项判断架构、API、数据、配置、业务流程、状态机、UI、埋点、测试、构建、部署和目录是否受影响，并列出需要同步的文档（见 AGENTS.md 代码-文档映射）。
- 修改中若实现偏离计划，立即调整文档范围，不得等到收尾时靠记忆补写。
- 修改后必须记录：本次改动、受影响模块、已更新文档、无需更新文档及理由、仍存在的不一致。
- 禁止代码已变而文档仍是旧逻辑，也禁止把计划或猜测写成已实现。

## 推荐规则

- 纯计算与视图分离，优先复用已测试的转换函数。
- 异步使用 `async/await`，在最能补充上下文的边界捕获错误。
- 修改范围保持最小；重构与行为变更尽量拆开。
- 性能优化先记录基线，再增加防回归测试。

## 例外

- 紧急线上止损可先最小修复，但必须更新 handoff、补回归测试并记录未完成的根因处理。
- 纯文案或静态展示修改可以不新增单元测试，但必须运行已有相关检查并人工核对。

## 项目专属规则

- Agent ID 必须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。
- 外部进程必须使用 argv 数组且 `shell: false`。
- Runtime provider 在创建后不得普通修改。
- Registry 与 `agent.yaml` 的身份/runtime 不一致时不得运行。
- 任何新的 chat/run/Bridge/Job 入口都必须复用 ExecutionContext 隔离环境。
- CLI 和 `/api/v1` 只能通过 `FactoryApplication` 调用业务用例，不得在路由或组件中重复路径、存储或进程编排。
- Web server 必须显式绑定 `127.0.0.1`，修改请求必须通过会话、Host、Origin 和 CSRF 检查。
- Secret、备份密码和任务提示不得进入 URL、localStorage、Registry 或 Operation DTO。

## 任务规模分级

按风险而非代码行数判断。涉及生产数据、密钥、DDL、权限或发布时一律按大型任务处理。

- **小任务**：单一文件或局部行为，风险低、边界清晰。可简短分析后直接实施，运行针对性测试。
- **中型任务**：跨多个文件或一个完整模块，影响 API、状态或数据口径。必须列计划、影响范围和验证矩阵。
- **大型任务**：跨架构、迁移、存储、发布、权限或不可逆操作。先审计和方案，经用户确认后分阶段实施并设置回滚点。

## 禁止行为

- 直接修改生产数据、执行 DDL、发布或推送，除非用户明确授权。
- 破坏性 Git 回滚、覆盖未知工作树改动或为了通过测试删除断言。
- 把当前实现自动宣称为最终产品规则；证据不足时必须标记待确认。
